# Documenting d2e features

Every user-visible d2e feature gets documented on the docs website, in the same
branch/PR as the implementation — documentation written later is documentation
never written. Document what was BUILT (read the plan and the diff), not what
was planned.

## Where

`<d2e repo>/docs/website` — a Docusaurus site (`docusaurus.config.ts` at its
root). Key fact: **the sidebar is autogenerated from the folder structure**
(`sidebars.ts` uses `{type: 'autogenerated', dirName: '.'}`), so file placement
and numeric prefixes ARE the navigation — there is no sidebar file to register
a page in.

Layout (verified):

```
docs/website/docs/
  0-getting_started/          README.md
  1-user_guide/               numbered subsections, e.g.
    0-Introduction  1-User_Interface  2-Datasets  3-Concepts
    4-Cohorts  5-Notebooks  6-Analysis  7-Account_activities
  2-admin_guide/              0-users  1-datasets  5-setup  6-knowledgebase
```

Pick by audience: end-user features → the matching `1-user_guide` subsection;
operator/configuration features → `2-admin_guide`. Extend an existing page when
the feature belongs to an existing topic; create a new numbered page/directory
(following the neighbors' numbering) only for a genuinely new topic.

## How

1. Read the surrounding pages first and match their voice: task-oriented
   sections, concrete steps with real values, plain markdown, one `#` title.
   No marketing language.
2. Images live next to the pages (`images/` dirs) or under `static/img`; link
   relatively so the build verifies the links. If the feature changes existing
   screenshots, note them as outdated rather than describing images you cannot
   produce — or capture real ones with the `testing-d2e-ui` flow when the
   change is visual.
3. Update content the feature obsoletes — a new option changes existing pages'
   steps; stale instructions are worse than missing ones.

## Verify

From `docs/website`: `npm install` (first time) then `npm run build` —
Docusaurus fails the build on broken links/anchors, which is the point.
`npm start` serves a live preview if a human wants to look.

## Ship

Commit the docs changes on the SAME feature branch/worktree as the
implementation so they ride the same PR and review. Docs for a feature that
lands in a different PR drift immediately.
