# CLI

`trex` is the command-line tool for managing a Trex deployment. It is a fork of
the Supabase CLI and exposes the same command surface (`trex login`, `trex link`,
`trex functions deploy`, `trex secrets`, `trex gen types`, `trex config push`)
pointed at the [Supabase-compatible management API](apis/functions#management-api-supabase-cli-compatible)
that Trex implements.

The fork's source lives under `plugins/cli/` of the trexsql repository. Releases
are published as the npm package `trex`, plus deb/rpm/apk/archlinux packages
generated by GoReleaser.

:::note Two tools named `trex`
There are two separate binaries called `trex`:

1. **The management CLI** (this page) — the Supabase-CLI fork, npm package
   `trex`, for managing a remote deployment (`login`, `functions deploy`,
   `secrets`, `gen types`, …).
2. **The server launcher** — npm package `@trex/cli` (source `plugins/bao`),
   which runs the Trex server inside the Docker image via `trex serve`. See
   [Server launcher](#server-launcher) below.

Same command name, different tools and disjoint command sets. This page is the
management CLI unless a section says otherwise.
:::

## Install

### npm

```bash
npm install -g trex
trex --version
```

The postinstall script downloads the platform-specific binary from the matching
GitHub release.

### Build from Source

`plugins/cli` is a git submodule (upstream `github.com/p-hoffmann/cli.git`). It
is not checked out by a plain clone — initialize it first:

```bash
git submodule update --init plugins/cli
cd plugins/cli
go build -o trex
./trex --version
```

### Upstream Supabase CLI

Because the management API surface is Supabase-compatible, the upstream
`supabase` CLI (≥ v1.200) also works against a Trex server. The two binaries
share the same on-disk config layout (`supabase/config.toml`) and `SUPABASE_*`
environment variables, so you can switch between them without re-running `init`.

## Login

The CLI authenticates with a personal access token (`sbp_…`). Trex issues these
through an ECDH-sealed device-code flow:

```bash
trex login --use-api http://localhost:8001
```

The command opens your browser to the Trex login page, where an admin user
approves the request. After approval the CLI receives the encrypted token and
stores it locally. See [CLI Login Flow](apis/functions#cli-login-flow)
for the cryptographic details.

For non-interactive setups, generate a token via the web UI
(Settings → API Keys, prefix `sbp_`) and export it:

```bash
export SUPABASE_ACCESS_TOKEN=sbp_…
```

## Linking a Project

Trex exposes a single synthetic project (`ref = trexsqldefaultlocall`):

```bash
trex link --project-ref trexsqldefaultlocall \
          --use-api http://localhost:8001
```

This populates `supabase/config.toml` with the Trex endpoints and pulls down the
current auth / database / storage configuration.

## Common Commands

### Edge Functions

```bash
# Create a function locally
trex functions new hello-world

# Deploy a function
trex functions deploy hello-world

# Invoke a deployed function
trex functions invoke hello-world --data '{"name":"world"}'

# Download a deployed function (returns the ESZIP bundle, or source if no bundle)
trex functions download hello-world

# Delete a function
trex functions delete hello-world
```

### Secrets

```bash
trex secrets list
trex secrets set MY_API_KEY=… ANOTHER_VAR=…
trex secrets unset MY_API_KEY
```

Secrets land in `trexdb.secret` (encrypted) and are injected into every edge
function worker.

### Database Connection

```bash
# Start a one-hour scoped Postgres role and print psql connection info
trex db connect --use-api http://localhost:8001

# Generate Supabase-style TypeScript types from your Postgres schemas
trex gen types typescript --schema public,trex
```

### Configuration

```bash
# Pull the current server config into supabase/config.toml
trex config pull

# Push local changes back
trex config push
```

`config push` updates rows in `trexdb.setting` for the auth / Postgres / PostgREST
/ storage sections.

## Compatibility Notes

- The `trex start` / `trex stop` commands manage local Docker containers, which
  is unrelated to a remote Trex server — they emulate the local-stack workflow
  inherited from the Supabase CLI fork.
- Several Supabase-specific endpoints are stubbed
  (`/v1/projects/:ref/network-restrictions`, `/billing/addons`, etc.) so commands
  like `trex config push` succeed without the underlying feature being
  implemented.
- Branching, point-in-time recovery, and GoTrue advanced flows are not
  implemented.
- The on-disk config directory is named `supabase/` (not `trex/`) so the upstream
  Supabase CLI can also be used against the same project without re-running
  `init`.
- The Go module path of the source remains `github.com/supabase/cli` (the
  upstream fork path). This affects `go install` invocations but is invisible
  to end users of the published `trex` binary.

## Server launcher

Distinct from the management CLI above, the **`@trex/cli`** package (source
`plugins/bao`) provides the `trex` binary that launches the Trex server. This
is the command the Docker image runs; you rarely invoke it by hand unless
running the server outside a container. It's a thin wrapper around a
self-contained JVM build (`trex` → `java -jar trexsql.jar`), and also ships a
`tbuild` helper.

### `trex serve`

Start the server (the default subcommand). Runs the Trexas HTTP server and the
pgwire endpoint, loads extensions, and orchestrates services.

```bash
trex serve --trexas-port 9876 --pgwire-port 5433 --main-path ./main
```

Common flags:

| Flag | Default | Description |
|------|---------|-------------|
| `--trexas-host` / `--trexas-port` | `0.0.0.0` / `9876` | Trexas HTTP bind address/port. |
| `--pgwire-host` / `--pgwire-port` | `0.0.0.0` / `5433` | pgwire bind address/port. |
| `--main-path` | `./main` | Main service directory / bundle. |
| `--event-worker-path` | — | Event worker directory / bundle. |
| `--tls-cert` / `--tls-key` / `--tls-port` | — / — / `9443` | TLS termination. |
| `--worker-policy` | `per_worker` | `per_worker`, `per_request`, or `oneshot`. |
| `--max-parallelism` | — | Max worker parallelism. |
| `--extensions` | — | Extensions to load. |
| `--swarm-config-path` | — | Path to a swarm config file. |
| `--enable-inspector` / `--inspector-*` | — | Enable the V8 inspector. |
| `--no-orchestrator`, `--no-pool` | — | Disable service orchestration / the connection pool. |

### `trex cache`

Cache an external database into a local file. `cache create`, `cache status`,
`cache cancel`, with flags including `-s/--source`, `-j/--jdbc-url`,
`-d/--dialect`, `-S/--schema`, `-t/--tables`, `-b/--batch-size`,
`-c/--cache-path`, `--json`.

```bash
trex cache create --source omop --jdbc-url "jdbc:postgresql://db/omop" --dialect postgres --schema public
```

### `trex bundle`

Compile a TypeScript/JavaScript entrypoint into an `.eszip` bundle:

```bash
trex bundle -e ./functions/hello/index.ts -o ./functions/hello/index.eszip
```

### `tbuild`

Project builder. Reads a project's `package.org.json`, bundles each declared
function via `trex bundle`, and writes an updated `package.json`.

### Environment

The launcher reads: `TREXSQL_JAR` (jar path override), `TREX_SQL_PASSWORD`
(required — server startup is skipped if unset), `TREX_EXTENSIONS_PATH`,
`TREX_ROUTES` (JSON proxy routes), and `TREX_INIT` (JSON init config).

## Plugin Source

`plugins/cli/` ships the source of the Trex CLI fork. Build artifacts are not
included in the runtime image — the CLI is a developer tool, not a runtime
service. `plugins/cli` is a git submodule (upstream
`github.com/p-hoffmann/cli.git`) — run `git submodule update --init plugins/cli`
before building. See [`plugins/cli/README.md`](https://github.com/p-hoffmann/cli/blob/develop/README.md)
for build details.
